# Itadaki Atlas コンテンツ制作・投入

## 0. 前提: このページは何のためにあるか（毎回ここから）

North Star: **浅い興味の人を「深く」か「広く」のどちらかに一歩進ませて後段（food-recommend / deep-local）へ渡す**。読了・満足・離脱は失敗。

- **深く** = その食べもの自体への深さ。**食べてみたい / どんな味か / どう作るのか / なぜこの形になったのか**
- **広く** = 外に出る。この土地の他の食、使っている素材・仕込み

詳細ページはこの2方向の分岐点。書く文章は「読ませるため」ではなく「この2方向のどちらかに動かすため」に書く。

## 1. 何を書くか（採否の判定基準）

**判定は一文で: これを知って食べると、その一口が変わるか。**

| 書く（正体の説明） | 書かない（正体と無関係） |
| :--- | :--- |
| 味・食感・食べ方・温度 | テレビ・雑誌での紹介、受賞歴 |
| 何でできているか、なぜその材料か | チェーン展開・店舗数・全国区になった経緯 |
| 作り方・技法とその理由 | 年表的な出来事の羅列 |
| 起源・伝来と、そこからの独自発展（例: 天麩羅のポルトガル由来→日本での変化） | 有名人の逸話 |
| 土地の条件がその形を生んだ因果（寒さ→脂の膜、保存食→味噌） | ランキング・優劣・「日本三大」を当サイトの評価として言うこと |

歴史は年表ではなく**「この一品がこうなった理由」としてだけ**書く。独立した歴史章を立てず、味・構成・作り方の説明に織り込む。

## 2. 文体

- **断定しない。**「一説によると」「〜と伝わる」「〜とされる」を既定にする。ほぼ全ての郷土食に複数の伝承がある
- **説が割れているなら、割れていること自体を書く**（「三平の賄いが原型と伝わるが、屋台街で同時期に生まれたという見方もある」）。資料集としての誠実さであり、読み物としても面白い
- **事実と伝承を混ぜない**。材料・製法・現在の姿は事実として、起源は伝承として書き分ける
- 文章はすべて書き下ろし（転載禁止）。日英とも各言語で書く（直訳しない）
- 凝った見出しを発明しない。UIの語は普通の語（目次・構成・つながり）。凝るのは本文だけ

## 2.4 土地との結びつきの3種別（地図に載る理由）

判定は一文で: その土地で食べる理由を一文で言えるか。言える内容によって3種別に分かれる。

| 種別 | 意味 | 表現 |
| :--- | :--- | :--- |
| 発祥 | ここで生まれた・固有の型（ひつまぶし＝うなぎめしの固有型） | 発祥ピン（lat/lng） |
| 産地 | ここが育てる・仕込む | food_item_regions（relation_type='名産地'） |
| 本場 | どこでも食べられるが、ここのは特別 | food_item_regions（relation_type='本場'）。note_ja/note_en 必須・地域ページでは第4群表示 |

- **本場は構造的な理由の一文＋出典が必須**（例: 金沢の寿司＝近海の水揚げと市場が近い／浅草のうなぎ＝江戸期からの専門店の集積）。「美味いから」だけでは載せない——ランキング禁止と両立させるための条件
- **国民食型**（発祥は歴史として語れるが現在は全国区。海鮮丼・寿司一般など）は発祥ピンを置かない。ピンなしアイテム（lat/lng NULL＝図鑑枠）＋本場の複数県紐付けで表現し、発祥の物語は本文で語る
- どの土地の因果も言えないもの（どこで食べても同じ）はアイテムにしない。総論はジャンルページの説明文が受け、郷土型・本場へ渡す
- 地域限定チェーン（静岡のさわやか等「そこでしか食べられない」）は chains の地域限定フラグで該当地域ページに出す
- 投入: 本場行は `data/<item>-regions.csv`（note_ja/note_en/source_url 列つき）→ `scripts/import-regions.ts`。source_url 付き行は food_item_sources にも記録される。座標は市場等の実在ランドマークに置く

## 2.5 タグと本文の分担

- **タグは客観的に一意に決まる値だけ**。同じ品を10人が見て同じ値になるか、が判定基準（例: 濃厚●●●○ は系統内の相対尺度として定義すれば可、麺の形状は観察できる事実）
- **主観・店差はタグにしない**（「にんにくあり」=店ごとに違う、「最後まで熱い」=所感）。ブレるタグはフィルタとして機能せず比較を壊す
- 味わい・食感・食べる時の感覚は**本文で書く**。タグ=フィルタと比較のための値、本文=味わいを伝える言葉。役割を混ぜない

## 3. データの規律

1. **全アイテムに出典必須**（URL実在確認。自治体・観光協会・組合・発祥店公式 > 大手メディア > Wikipedia最終手段）。ただし**出典はDB内部の検証データでページには表示しない**（誤情報・リンク切れの露出回避。UIは「訂正を送る」のみ）
2. **三点セット**: name_ja・name_romaji・name_en（説明訳。固有名詞の転写を name_en にしない）
3. 企業単一ブランドの商品は図鑑アイテム（food_items）にしない。保護対象・規制種は不掲載
   - ただし有名チェーンは**橋渡しコンテンツ（chains・別テーブル）として掲載してよい**。「このチェーンの味が好きなら、この系統・ご当地へ」という入口装置であり、図鑑の一員ではない。事実ベース（系統・創業地は出典確認）・優劣なし・推薦先はDB実在アイテム/系統のみ
4. 正確さ > 網羅性 > 速度

## 4. 情報構造（2026-08 確定）

- **タグ一元 + 排他棚1本**: 棚28本（料理10・食材9・仕込み9）は全アイテム必須・1つだけ。URL・地図記号・数え上げの単位
- **ジャンル昇格制**: 同型20件以上 + 実在の呼び名（造語禁止）で棚内「その他」から昇格。データ移動のみ
- **関係4語彙**: 源流/派生・兄弟・対比・使う⇄使われる。公開条件 = 関係・名産地・同県のいずれか1つ以上（行き止まり禁止）
- 3群記号: ●料理（生まれた）/ ■食材（育てる）/ ◆仕込み（仕込む）
- **意味のない分岐を作らない**。ジャンル別の見出しテンプレ・型分類などは、単一の普通の表現で壊れる証拠が出るまで作らない

## 5. Tier制（均一を約束しない）

| Tier | 内容 | 対象 |
| :--- | :--- | :--- |
| 1 | 三点セット・座標・要約・タグ | 全アイテム（標準） |
| 2 | + 本文（味・構成・作り方・起源） | 検索需要・話題性の高いもの |
| 3 | + 図解・厚い本文 | 各ジャンルの看板数件 |

本文は章立て自由のMarkdown。Tier1でもページが欠けて見えない設計なので、薄いまま出してよい。

## 6. 投入手順

```bash
cd itadaki-atlas
bash -c 'set -a; source .env.local; set +a
npx tsx scripts/import-genres.ts --file data/genres.csv
npx tsx scripts/import-food-items.ts --file data/<genre>.csv --genre <genre-slug> --dry-run  # 三点セット全列を目視
npx tsx scripts/import-food-items.ts --file data/<genre>.csv --genre <genre-slug> --publish'
```

- CSV生成は**pythonのcsvモジュール必須**（name_en にカンマが入る。手書き処理で全行破損した事故あり）
- **slugはグローバル一意**。地名だけのslugはジャンル間で衝突する（博多うどんが博多ラーメンを上書きした事故あり）→ `<地名>-<ジャンル>` 形式にし、投入前に既存slugと突合する
- 投入後: 対象ページの生成確認 → `npm run test:e2e` 全件。「掲載なし県」前提のテスト（現在=石川）はデータで埋まったら更新する

## 7. 量産

`research-fleet`（グローバルSkill）の体制で回す。指示書には本Skillの **1〜3節（採否基準・文体・データ規律）とslug/CSV規則を全文転記**すること（部隊は会話文脈を持たない）。
