# 目的

Itadaki Atlas の事業戦略（マネタイズ・マーケティング・Lean検証）を定義する。

## 1. マネタイズ方針

### 1.1 採用しないもの（確定）

| 不採用 | 理由 |
| :--- | :--- |
| **メーター型ペイウォール** | SEO資産化と正面から衝突する。読めないコンテンツは検索流入も送客も生まない |
| **広告除去課金** | 同上。そもそも広告を主体にしない |
| **バナー広告** | 中立性と体験を両方損なう。単価も低く、必要なトラフィック規模が現実的でない |

### 1.2 本線: 全コンテンツ無料開放 → 既存事業への送客

```
SEO / SNS → Itadaki Atlas（全無料）→ 送客 → 既存事業で収益化
                                    ├─ deep-local（旅程プランニング）
                                    └─ food-recommend（ラーメンエージェント）
                                    └─ 店舗予約手数料
```

**Itadaki Atlas 単体で黒字化することを目標にしない。** 集客上流・信頼資産としての役割を担う（`.doc/00_concept/01_north_star.md`）。

インフラコストが月10万PVまで実質$0、100万PVでも月$20〜45に収まるため、**この構造が財務的に成立する**（`.doc/10_system/02_infrastructure.md` §3）。トラフィックが増えても赤字が膨らまない。

### 1.3 育成後: PR / タイアップ

トラフィックとコンテンツが育った段階で開く収益線。

| 商材 | 内容 | 制約 |
| :--- | :--- | :--- |
| **スポンサー店舗枠** | 各アイテムページ最上部に「実際に食べるならこの店」を**1枠限定**で販売 | **「PR」表記必須**（ステマ規制対応）。イラスト解説の中立性は維持し、元祖店の編集掲載とは別枠 |
| **実写掲載** | イラストを実写に差し替える権利を出稿商材化 | 画像権利問題とマネタイズを同時に解決する構造 |
| 企業・自治体タイアップ | レコメンド枠・特集制作 | 中立性を毀損しない範囲 |
| 観光庁系補助事業・DMO委託 | 相乗り | — |

営業は「**既に掲載済み + トラフィック実績**」を武器に展開する。掲載してから売るので、飛び込みではなく実績提示になる。

**規制対応済みであること自体が営業上の信頼材料になる。** 中立性はコストではなく商品価値の一部（`.doc/00_concept/01_north_star.md` §2）。

### 1.4 補助線

制覇マップ・保存等のプレミアム機能（フェーズ3）。本線ではない。

## 2. マーケティング

### 2.1 SEOが主戦場

2つの正面を持つ。

| 正面 | クエリ例 | 対応ページ | フェーズ |
| :--- | :--- | :--- | :--- |
| **ジャンル軸** | "types of ramen" / "sushi types" | `/[genre]`, `/[genre]/[slug]` | 1 |
| **エリア軸** | "what to eat in Niigata" | `/region/[pref]` | 1（実装済み） |

エリア軸は旅行者クエリを直接取りに行くもので、**インバウンド旅程プランニングへの送客距離が最も短い**（軸→出口の対応は `.doc/00_concept/02_vision.md` §4 成長モデル）。ページはデータドリブンで実装済み。読み物の厚みはフェーズ2で金沢/石川から。

### 2.2 SNS

サイトは「静かな参照先」に保ち、**交流はSNS側で起こす**（`.doc/40_operation/01_strategy.md`）。

- 対象: X / Instagram / TikTok / YouTube（ハンドルは `@itadakiatlas` で統一取得）
- **部位図鑑の解剖図イラストは投稿素材として最も強い**（フェーズ3の焼き鳥展開時）。地図とは別軸のビジュアル勝負ができる

### 2.3 日本語版の位置づけ

日本語版は「英語版のおまけ」ではなく**主力コンテンツ**として扱う。品質基準「日本人としても見たいレベル」を守れば国内でも話題になり、国内トラフィック自体が資産になる（`.doc/00_concept/03_market.md` §4）。

## 3. Lean検証戦略

### 3.1 MVPで検証すること

フェーズ1（ラーメン約180種）で検証する仮説は**「ジャンル軸 × 地図」の型が成立するか**である。

| 検証項目 | 判定材料 |
| :--- | :--- |
| 地図UXが使われるか | 地図操作率（ボトムシート展開率） |
| 検索に載るか | GSCインデックス数・オーガニック流入 |
| 深さが評価されるか | SNS反応・滞在時間 |

**写真なしで開始する**のは、この3点の検証に写真が必須ではないため。画像調達を待たずに型の検証を先に回す。

### 3.2 展開順の判断基準

型が検証できたら他ジャンルへ広げる。順序は3つの基準で決める（詳細な登り順は `.doc/99_management/01_roadmap.md`）。

1. **重複項目の多さ** — 既存の詳細テーブルを流用できるか（実装コスト）
2. **既存事業とのシナジー** — 送客先が実在するか
3. **検索需要** — 英語圏のクエリボリューム

## 4. スコープ規律

拡大の誘惑に対する歯止めを明文化しておく。

- **食以外に広げない**（温泉等）。ただし食側からの接続は可（温泉地×湯豆腐・地獄蒸し）
- 純粋な温泉マップが必要になったら、**Itadaki ブランドの別サービス**として切り出す。本プロダクトに混ぜない
- コメント欄・アカウント機能を「あったほうが良さそう」で入れない。必要性が実証されてから
