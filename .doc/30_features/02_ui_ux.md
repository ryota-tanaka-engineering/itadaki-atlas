# 目的

Itadaki Atlas の画面構成・操作体系・URL設計を定義する。デザイン実装の一次情報源。

## 1. 設計の起点: スマホファースト

主対象は**移動中の海外旅行者**であり、利用シーンはスマホが前提。PC を後回しにはしないが、レイアウトの起点は縦画面に置く。

## 2. 基本構成: フルスクリーン地図 + ボトムシート

地図を常に全画面の背景に置き、索引・詳細は下からのドラッグ可能なシートに載せる。**ページ遷移なしで地図と詳細を往復**できることが体験の核心。

```
┌─────────────────┐
│ [ラーメン][寿司] │ ← 上部: ジャンル切替チップ（横スクロール・浮かせる）
│                 │
│      地図       │ ← 常に全画面背景
│    （ピン）     │
│                 │
├─────────────────┤
│ ━━━             │ ← ボトムシート（ドラッグ可能）
│ 札幌味噌ラーメン │
└─────────────────┘
```

### 2.1 ボトムシートの3段階スナップ

| 段階 | 状態 | 用途 |
| :--- | :--- | :--- |
| **ピーク** | 下部に僅かに表示 | 地図を最大限見せる。ピンタップ時のアイテムカード |
| **ハーフ** | 地図半分 + リスト半分 | 地図とリストを見比べる |
| **フル** | 実質リストページ | 索引を読む・詳細を読む |

### 2.2 操作フロー

```
ピンをタップ
  → シートがピークに上がり、アイテムカードを表示
  → 引き上げるとフルになり詳細表示
  → 下げると地図に戻る（ページ遷移なし）
```

上部にはジャンル切替の横スクロールチップのみを浮かせる。それ以外のUIは地図の上に置かない。

## 3. 縦画面 × 日本列島問題への対応

日本列島は**細長く斜め**なので、縦画面で全国を俯瞰すると余白だらけになり「どこに何個あるか」が分からない。これを2種類の地図の切り替えで解く。

| ズーム | 地図 | 目的 |
| :--- | :--- | :--- |
| 全国俯瞰 | **ディフォルメ地図**（47都道府県を等サイズの格子に並べる） | 「どの県に何個あるか」の**一覧性** |
| エリア以下 | 実座標地図（MapLibre） | 「エリア内で探す」体験 |

ディフォルメ地図は MapLibre もタイルも使わない。**47個の図形を並べた SVG** であり、地図ライブラリとは無関係な通常のフロント実装として扱う。

**「選挙特番型」という喩えを使わない。** 格子配置という技法だけを指すつもりでも、優勢・当確・勝敗という意味論ごと持ち込んでしまう。この地図が示すのは**件数という事実だけ**であり、「この県は◯◯系が強い」のような優劣の断定はしない（`.doc/00_concept/05_brand.md` §4.1）。

- 県のセルを単一の系統色で塗らない。1県に複数系統がある場合（例: 北海道＝味噌・醤油・塩）、1色で塗ると事実でない断定になる
- セルが持つ情報は**件数**。系統は「その県に存在する系統」を並置するに留める

## 4. 索引

**地図と対等なビュー**として、同一データソースから生成する。地図の付属品ではない。

3軸で引ける:

| 軸 | 内容 |
| :--- | :--- |
| **五十音 / アルファベット順** | 言語に応じて切り替える |
| **地域別** | 都道府県・エリア単位 |
| **系統別** | 醤油 / 味噌 / 塩 / 豚骨 / その他 |

## 5. ビジュアル: 写真がない前提の設計

フェーズ1は写真・イラストを持たない。**系統色がアイコンの役割を担う**。

- ピンは主系統ごとに色分けする
- 索引のリスト項目にも同じ系統色を出し、地図とリストで**同じ色の言語**を使う
- 色だけに依存しない（アクセシビリティ）。系統名のテキストを必ず併記する

フェーズ2でイラストが入った際に、系統色を残すか置き換えるかは実装時に判断する。

## 6. アクセシビリティ

目標は **WCAG 2.2 AA 相当**。

| 項目 | 対応 |
| :--- | :--- |
| 地図の代替手段 | **索引がスクリーンリーダー向けの主要動線**。地図と同等の情報に到達できること |
| キーボード操作 | 地図ピンは `button` 要素とし、フォーカス可能にする |
| フォーカス管理 | 詳細パネル・ボトムシートの開閉時にフォーカスを適切に移動・復帰させる |
| 色 | 系統の識別を色のみに依存させない（§5） |

計測目標は Lighthouse a11y **90+**。

地図UIは本質的にスクリーンリーダーと相性が悪いため、**索引を後付けの代替ではなく最初から対等な経路として作る**ことでこれを解決する。

## 7. URL設計

```
/                       トップ: 全ジャンル統合地図 + フィルタ
/[genre]                ジャンル別地図 + 索引        （例: /ramen）
/[genre]/[slug]         アイテム詳細                 （例: /ramen/sapporo-miso）
/region/[pref]          地域ページ（実装済み・データがある県に自動で生える。例: /region/niigata）
```

- **i18n はサブパス方式**（`/ja/…` `/en/…`）。詳細は Platform `../.doc/10_system/10_growth_infra.md` §3
- `genres.slug` による**動的ルート1本で全ジャンルに対応**する。ジャンル追加でルーティングを増やさない

### ナビゲーションの二本立て

トップの入口は「**ジャンルから探す**」「**エリアから探す**」の2つとする。地図の県タップをエリア入口として使う。

エリア軸は "what to eat in Niigata" 系の旅行者クエリを取る**第二のSEO正面**であり、インバウンド旅程プランニングへの送客装置でもある。ページはデータドリブンで**実装済み**（F-11）。読み物としての厚み（地の文）はフェーズ2で金沢/石川から書き始める（`.doc/99_management/01_roadmap.md` P2-3）。
